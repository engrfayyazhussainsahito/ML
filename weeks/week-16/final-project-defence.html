Lesson 16.5: Final Project and Defence

Final Project Requirements

The final project defence is a 20-minute presentation of your capstone work followed by 10 minutes of questions. It should tell a coherent story: why the problem matters, what you did, what you found, and what you would do next. The audience includes both technical peers and non-specialist evaluators — your presentation must work for both.

Presentation Structure

presentation_outline = {
    "Slide 1 — Title (1 min)": [
        "Project title",
        "Your name",
        "One sentence: what problem you solved and why"
    ],
    "Slides 2-3 — Motivation (3 min)": [
        "Real-world problem with concrete stakes",
        "Why existing solutions fall short",
        "Your specific contribution"
    ],
    "Slides 4-5 — Data (3 min)": [
        "Dataset description (source, size, features, labels)",
        "Key EDA findings (1-2 figures)",
        "Data challenges encountered and how addressed"
    ],
    "Slides 6-8 — Methods (5 min)": [
        "Baseline and why you chose it",
        "Your approach and the reasoning behind it",
        "One key technical detail explained clearly"
    ],
    "Slides 9-10 — Results (4 min)": [
        "Main results table with baselines",
        "Error analysis: what the model gets wrong",
        "Ablation: which component matters most?"
    ],
    "Slide 11 — Limitations and Future Work (2 min)": [
        "What the model cannot do",
        "What you would try next with more time"
    ],
    "Slide 12 — Conclusion (1 min)": [
        "3 key takeaways only",
        "Link to code/demo"
    ]
}

Common Questions and How to Answer Them

questions_and_answers = {
    "Why did you choose this baseline?": 
        "Explain: it's the simplest sensible approach, establishes the floor, and is what a non-ML practitioner would do first. Good baselines are not weak — they are honest.",
    
    "Why not use model X instead?": 
        "Acknowledge X. Explain: given your data size/compute/interpretability requirements, your choice was appropriate. Offer to compare in future work.",
    
    "Is the improvement statistically significant?": 
        "Show confidence intervals. If you have them, explain the test. If you don't, acknowledge the limitation honestly.",
    
    "What would you do with 10x the compute?": 
        "Larger model, more hyperparameter search, additional data augmentation, self-supervised pretraining — show you understand the scaling dimension.",
    
    "How would you deploy this?": 
        "Describe: serving architecture, latency budget, monitoring plan, retraining schedule, A/B testing. This signals production awareness.",
    
    "What's the biggest limitation?": 
        "Answer honestly — evaluators respect self-awareness far more than defensiveness. Then explain how you'd address it."
}

Portfolio Publication Checklist

publication_checklist = {
    "Code": [
        "All notebooks run top-to-bottom without errors",
        "requirements.txt with pinned versions",
        "README with clear setup instructions (test on a clean env)",
        "No hardcoded paths or private credentials",
        ".gitignore: exclude data/, __pycache__, .env",
        "LICENSE file (MIT for open source)"
    ],
    "Documentation": [
        "README: problem, results table, how to run",
        "Model card: intended use, evaluation, limitations",
        "Inline docstrings on all functions",
        "Comments explaining non-obvious decisions"
    ],
    "Results": [
        "Results are on held-out test data only",
        "Confidence intervals or standard deviations reported",
        "Comparison to at least one reasonable baseline",
        "Honest discussion of failure cases"
    ],
    "Presentation": [
        "Demo or interactive notebook if possible",
        "Summary blog post (Medium, personal site, or LinkedIn)",
        "Link in GitHub profile README"
    ]
}

for section, items in publication_checklist.items():
    print(f"\n{section}:")
    for item in items: print(f"  [ ] {item}")
